# 修复 RBAC 权限检查逻辑

经过详细检查，发现 `SysPermissionService` 中的 `getRolePermission` 方法存在一处逻辑隐患，可能导致无法正确从数据库校验 `SUPERADMIN` 角色。

## 问题分析
1.  **现有逻辑**：
    在 `getRolePermission` 方法中，存在如下代码：
    ```typescript
    if (user && user.isAdmin) {
      roles.add('admin');
    }
    ```
    这段代码会检查 `user.isAdmin` 属性。如果为真，它将添加 `'admin'` 角色并**跳过**数据库查询。
2.  **不一致性**：
    后续的 `getMenuPermission` 方法检查的是 `'SUPERADMIN'` 角色（`roles.has('SUPERADMIN')`），而不是 `'admin'`。因此，如果触发了 `isAdmin` 逻辑，用户反而无法获得超级管理员权限（`*:*:*`）。
3.  **不符合需求**：
    您的需求是：“从 User 表中找出其关联的 Role 表是否有跟他绑定 SUPERADMIN”。现有的 `isAdmin` 捷径绕过了这一数据库检查。

## 修复方案
修改 `src/modules/permission/sys-permission.service.ts` 文件：
1.  **移除 `user.isAdmin` 判断块**：强制系统始终执行数据库查询，以检查用户与角色的实时关联关系。
2.  **保留数据库查询逻辑**：确保通过 `user_id` 关联查询 `SysRole` 表，并提取 `role_key`。
3.  **验证多角色支持**：现有的 `userWithRoles.roles.forEach` 逻辑已经支持一个用户拥有多个角色，无需修改。

## 预期行为
1.  无论 `user` 对象中是否携带 `isAdmin` 属性，系统都会查询数据库。
2.  如果数据库中用户关联了 `role_key` 为 `SUPERADMIN` 的角色，该角色将被添加到权限集合中。
3.  `getMenuPermission` 检测到 `SUPERADMIN` 后，赋予 `*:*:*` 权限。
4.  `PermissionsGuard` 检测到 `*:*:*` 后，放行所有请求。

这将完全符合您对 RBAC 和超级管理员权限控制的要求。
