# 代码复杂度

## 1. 深度诊断与逻辑分析

### 圈复杂度可视化
*   请分析代码中的深层嵌套、多重 `switch/if` 分支及复杂循环，直接指出导致逻辑拥堵的具体节点，而非通篇解释代码。

### 认知负荷评估
*   请审查变量命名、状态变更流向及隐式依赖关系，指出哪些代码写法不必要地增加了阅读者的理解难度和记忆负担。

### 控制流与热点定位
*   请用文字描述数据的流转路径，重点标记异常捕获与边界跳转逻辑，并识别出模块中最脆弱、最容易发生 Bug 的“高危区域”。

## 2. 重构与代码降维

### 多态替代条件逻辑
*   针对复杂的条件判断，请构思如何利用策略模式、状态模式或工厂模式来重构，说明如何通过抽象接口消除冗余的 `if-else` 语句。

### 函数拆分与单一职责
*   请识别“上帝函数”中可独立的逻辑块，建议符合单一职责原则的函数命名，并说明如何通过参数对象化（Parameter Object）来简化过长的参数列表。

### 卫语句与结构扁平化
*   请指出代码中何处可以使用卫语句（Guard Clauses）来提前返回，从而消除深层缩进，使核心业务逻辑的主干更加清晰。

## 3. 架构解耦与设计

### 依赖倒置与分层检查
*   请检查高层策略是否依赖了低层实现细节，建议如何引入抽象层（Interface）来反转依赖，并验证业务逻辑是否泄漏到了表现层或持久层。

### 副作用与纯度审查
*   请列出该模块所有的外部依赖（如全局变量、数据库调用、API 请求），评估其“输入/输出”纯度，并说明这些副作用如何影响了系统的可测试性。

### 绞杀者模式迁移策略
*   针对遗留的复杂系统，请制定基于“绞杀者模式”的迁移计划，描述如何建立拦截层（Facade）路由请求，以便逐步剥离旧逻辑而不影响现有业务。
